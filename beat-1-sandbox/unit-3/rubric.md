# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diagnosis matches the repro evidence | The plan's stated cause/diagnosis, compared against what the repro evidence (posted repro comment or house repro pack) actually demonstrates | The stated cause is one the repro evidence's own shown output supports or is at least consistent with. Fails if the diagnosis contradicts the repro evidence (blames a different mechanism than what the evidence shows failing), or asserts a cause the evidence never addresses at all. | required |
| Fixes the cause, not the symptom | The plan's proposed approach/change, compared against the diagnosed cause and where the repro evidence traces the failure to | The proposed change targets the actual mechanism the evidence identifies (the specific function/code path), not merely the visible symptom (e.g. catching or suppressing the resulting error rather than preventing it). Fails when the approach addresses only the symptom while the evidence points at a different underlying cause. | required |
| Change is bounded | The plan's explicit in-scope / not-in-scope statements and any files or areas it names touching | The plan names a specific, bounded set of files/changes proportional to the diagnosed cause, with an explicit not-in-scope line when the change could plausibly expand. Fails when scope is unbounded (e.g. "refactor the module" for a single-function bug), vague about which files change, or has no not-in-scope statement for a plan touching more than one area. | required |
| A stranger could start executing it | The plan's stated approach and order of work | A reader with no other context can name the first concrete action (a specific file, a specific change, or a specific already-validated method for pinning the precise change — e.g. "trace with `--debug`, which already shows X") without asking the author anything. Deferring the literal function/line name to a concrete, already-validated method named in the plan is not the same as having no nameable first step. Fails if the approach is described only as unspecific intent ("investigate and fix it") with no named location or method. | required |
| Test plan is decisive | The plan's test plan section, compared against the repro evidence's own reproduction steps | The test plan re-runs (or explicitly adapts) the repro evidence's actual steps and states an observable before/after outcome that confirms the fix. Fails if the test plan is vague ("test it works"), doesn't reference the repro evidence's real steps, or states no observable expected outcome. | required |
| Unknowns are stated honestly | The plan's risks/unknowns section, read against the approach and scope actually chosen — not against the diagnosis's own grounding, which "Diagnosis matches the repro evidence" already judges separately | The plan names genuine implementation or deployment risks the chosen approach introduces: who else might be affected by the touched code path, whether the fix could regress other behavior, environment or version considerations the approach depends on. This check does not require hedging the diagnosis's own certainty — a diagnosis stated as a reasoned inference from evidence, even without code-level proof, is judged by "Diagnosis matches the repro evidence," not here. Fails when the risk section is missing entirely, or clearly inadequate for the chosen scope (e.g. a change touching shared code with zero consideration of other callers). | required |
| Plan comment is thread-aware | The plan comment's text, the issue thread's highlighted maintainer comments, and the repo-facts block's stated contribution conventions and AI-use disclosure requirement | If a maintainer already suggested a direction in the thread, the comment engages with it (building on it, or explicitly explaining a different choice) rather than ignoring it, and the comment meets whatever the repo's stated conventions ask for, including disclosure if required. Fails if the comment ignores an already-stated maintainer direction, or doesn't meet a stated convention/disclosure requirement. | required |

## Verdict rule

Accept (ready to post and build from) only if every required check grades pass. Any required check that grades fail, or grades unclear (evidence genuinely absent from the package, not merely hard to find), makes the verdict reject. There are no preferred checks in this rubric.
