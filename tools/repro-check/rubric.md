# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Input matches what the issue reported | The exact input given in the issue body; the exact input shown in the report's preparation step | The report's input is identical to the issue's stated input, OR any deliberate variation is explicitly called out and justified as still exercising the same code path. When the issue's own input is not itself a stable, reusable artifact (e.g. an external/remote resource a stranger can't reliably re-fetch), a self-built minimal substitute counts as justified without a separate explanatory sentence, as long as the report's resulting output demonstrates the same underlying mechanism as the issue's own output (e.g. the same error text or message), not merely a superficially similar failure. Fails if the input differs from the issue's in a way the report doesn't acknowledge and the resulting output doesn't independently prove the same mechanism — especially when that difference plausibly explains a different outcome. | required |
| Actual behavior matches the reported failure mode | The issue's stated actual behavior (error type, message, stack trace if any); the report's shown command output | The shown output exhibits the same class of failure as the issue describes (e.g. an unhandled panic vs. a handled/graceful error are different classes, even if both are technically "an error"). An honest report that ran the issue's own input/steps but plainly states the failure did NOT occur, backed by the actual (non-matching) output, PASSES this check — a genuine cannot-reproduce is not the same failure as claiming a match while showing a different one. Fails only when the report claims or implies a match that its own shown output does not support. | required |
| Steps are followable by a stranger | The report's stated setup, input, and command, read as a stranger who has only this comment would read them | A reader could redo the steps without having to guess any detail that would change whether the reported behavior triggers — the exact command, and any input/config value that specifically causes the behavior. A detail that doesn't affect whether the bug triggers (an arbitrary-but-valid supporting value, when the actual operative trigger is a different, precisely-stated detail) does not need to be reproduced character-for-character or pasted as a full file, as long as the operative trigger itself is stated explicitly. Fails if any detail that would change the outcome if different is missing, vague, or only implied — not merely because a whole script/file wasn't pasted verbatim. | required |
| Every confirmation claim is backed by shown output | Every sentence in the report or claim comment asserting the issue's reported behavior did or did not occur (e.g. "also confirmed on version X") | The claim about the issue's core reported behavior is backed by shown output somewhere in the report. A secondary remark that only repeats the SAME outcome already established by shown output (e.g. additional trials meant to rule out flakiness, not a new or different result) does not need its own separately-pasted run, and neither does a remark that adds no new specific fact beyond what's already shown. Fails when a claim introduces a new or different specific result (a number, a state, an outcome) beyond what's already shown, or when an unbacked claim is what the report's overall confidence actually rests on. | required |
| Conclusions don't overstate the shown evidence | The report's Analysis/Expected/Actual sections and the claim comment's stated confidence, compared against what the quoted output actually demonstrates | The stated conclusion is an accurate characterization of the artifacts actually shown. Fails if the narrative claims the bug is confirmed, reproduced, or understood when the quoted output doesn't support that — regardless of how confidently or fluently it's written. | required |
| Discloses AI assistance where the repo requires it | The repo's stated contribution policy / AI-use policy in the repo-facts block; whether the claim comment or report discloses AI involvement | If the repo's policy states no disclosure requirement, or states none at all, this check passes regardless of disclosure. If the policy explicitly requires disclosing AI assistance, this check fails when the comment or report contains no such disclosure. | required |
| Follows the repo's bug-report template | The repo-facts block's stated template fields (version, OS, install method, concise input, command, actual, expected) | Report includes all fields the template asks for | preferred |
| Tested version is current, or staleness is justified | The report's stated tool/library version against the repo-facts block's latest release and the version the issue was originally filed against; whether the issue or its bug-report template asks for confirmation on the latest version or main branch; any reasoning the report gives for testing an older version | Passes if the tested version is the latest release, OR — when the repo's own bug-report template does NOT explicitly demand confirmation on the latest release/main branch — the tested version is newer than the version the issue was originally filed against, with the report saying so. Fails when the repo's template explicitly demands latest/main confirmation and the report doesn't meet or acknowledge that, or when the tested version isn't even newer than the issue's own originally-filed version, with no justification given. | required |

## Verdict rule

Accept (ready to post) only if every required check grades pass. If
any required check grades fail, or grades unclear (evidence genuinely
absent, not merely unquoted), the verdict is reject (hold). Preferred
checks never change this verdict — report their grades and use them
only to note polish or completeness in the summary.
